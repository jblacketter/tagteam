What else makes the project better: engineering health and adoption

The features pages assume a codebase that can take them. This page is the honest look at the base: size, test time, the reliability items already in the backlog, docs, and what "better" means for a project whose second purpose is to be a portfolio.

1. Suite time is round time

Every submission pays ~4 minutes for the gate, and every reviewer turn that runs tests pays part of it again. That is wall clock on every round of every phase, and it is the single number that would make the loop feel faster.

  • Measure first: pytest --durations=25. The watcher, session, headless and port-lease tests likely sleep or poll; those are the candidates.
  • Parallelism: pytest-xdist if the tests are as isolated as "no fixtures package, no conftest tricks" suggests. Tests that touch ~/.tagteam or real ports need a marker and a serial group.
  • Gate profile: a gatekeeper.tests.quick command for plan cycles and bounced re-submissions, with the full command kept for the round on the record. The one-run rule stays intact; only the round that already bounced gets a faster retry.

Target: gate under two minutes. That alone shortens every round by two minutes on both sides.

2. Reliability items already known

Three backlog entries describe real incidents in the wake path. They are the things most likely to make a headless night fail silently, which matters more once the digest (features #1) makes overnight runs the norm.

iTerm2 cd eaten at shell startup

Reproduced 2026-09-04. The fix is named in the note: gate the cd on prompt readiness, verify session.path before launching the agent. One impl cycle.

Reviewer wake delivery

Observed once (2026-08-30), ruled a possible one-off. The diagnostics the note suggests would cost less than the next occurrence. Ship the diagnostics, not the fix.

Busy-detection by screen scrape

BUSY_PATTERNS/IDLE_PATTERNS match CLI spinner text. Both CLIs change their UI; a pattern that stops matching turns into a stuck turn. A tiny fixture test per CLI version (captured screens in tests/fixtures/screens/) would catch drift on upgrade.

3. The watcher is the file to be careful with

At 1,791 lines it holds five backends, busy detection, the watchdog, the headless engine hand-off, the gate seam and the panel seam. Every feature on the other pages that says "at the watcher's reviewer seam" adds to it. Not a rewrite (your rule), but the next phase that touches it should pull the seams into their own module (seams.py: gate → panel → dispatch, as a pipeline over one Submission object) so the model-policy work has one place to hook. Say this in the plan cycle for that phase, not as its own phase.

4. Docs: one long page is doing three jobs

docs/how-tagteam-works.md is the reference, the tutorial and the changelog in one file, with version numbers inline ("since 3.5", "3.8 — Phase 45"). It is accurate, which is rare, and it is hard to read cold.

  • Keep it as the reference. Move the "since X.Y" history to docs/releases/ (already started with 3.12.0).
  • Write a five-minute first session page: install, setup, start, first handoff, first review, the two commands you will actually type. The README is close; the how-it-works page is not the place.
  • Run doc-drift before each release and record it in the release note. It costs a Sonnet turn and catches the kind of thing the 3.12.0 role-neutrality work was about.

5. Release and install hygiene

  • 3.12.0 is installed locally and untagged. The publish workflow rejects a tag that disagrees with pyproject.toml; the release script bumps both. Tag it or revert the bump so the next session starts clean.
  • Two installs on one machine bit you in August (a stale cockpit). The SessionStart hook now warns on plugin/CLI skew; extend the same check to uv tool vs pip installs (tagteam doctor, which Phase 53's diagnostics could own).
  • The Windows job stays manual per your standing decision; run it before any release touching procs, headless, pidfiles or port leases, and say so in the release checklist.

6. Adoption and the portfolio

Tagteam's second job is to be public proof of how you work. Three things would raise its value there without new engineering:

  • A showcase that shows the loop getting cheaper. The Health tab (features #12) over your own phases is the graph nobody else has: rounds per phase, bounce rate, cost per phase, across 54 phases of a real tool built by the tool.
  • One case study per project type. Aegis (uv, Python), Northstar (Behave suites, production), SonicGrid. Each is a page: what the loop caught, what it cost, what escalated to you and why.
  • Name the role swap. Codex-lead / Claude-reviewer since 2026-09-09 is an experiment worth writing up with numbers from #2. Which pairing produces fewer rounds is a question people will ask.

7. What I would not do

  • Rewrite the cockpit in a framework. 1,481 lines of plain JS with SSE is the right size for one user and no build step.
  • Add an API-key path beside the CLI path. Subscription CLIs are the product's premise; a second auth path doubles every adapter.
  • Move the DB off SQLite. Phase 28 made it canonical and it has been quiet since.
