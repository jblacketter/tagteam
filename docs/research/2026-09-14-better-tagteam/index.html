Better tagteam: where the next weeks should go

Four pages, one argument. Tagteam's loop works and is well instrumented; what it lacks is the use of its own instrumentation. Measure a phase, grade a review, replay history as an eval, and every other decision on these pages (which model, which effort, which cockpit card) stops being a guess.

The argument in five points

1. Your instinct about cheap models is right, narrowly

Test running, codebase search and summaries do not need a frontier model, and the gate already runs tests with no model. Correctness review, authoring and your chat with the lead do. For those, lower effort on the frontier model is the measured cheaper path, not a weaker model. → Agents & models

2. Zero-code experiment available tomorrow

The headless adapter already accepts --model, --effort and --fallback-model in agents.<role>.headless.args. Set the reviewer to --effort medium and run one phase. → step 0

3. The biggest lever is round count, not price per token

A reviewer turn on this repo averages 595k input tokens, 90% from cache. A missed bug costs a whole extra round on both agents plus a four-minute gate. Anything that removes a round (self-review pre-flight, better lenses) beats anything that discounts one.

4. Your handoff history is an eval set you have not used

Every round in docs/handoffs/*.jsonl is a labeled example. A tagteam bench that replays reviewer packets at different model × effort cells turns "should scope run on Sonnet?" into a table. → Features #3

5. The cockpit needs one more pass, aimed at the morning

The August passes made a running cycle legible. What is missing is the delta: "what happened while I was away, what did it cost, what needs me". A digest card, one primary action, a collapsed idle reviewer lane, and a usage tab that shows the window instead of a churn line. → Cockpit UX

Underneath: suite time is round time

The gate's ~4 minutes is paid every round. Profile, parallelize, add a quick profile for bounced retries. Target under two minutes. → Engineering

What is verified and what is not

Read from the code, the DB or current docs

  • No model names are hardcoded; selection is per-role via validated args (headless.py).
  • --model, --effort, --fallback-model already allowed for Claude; -m for Codex.
  • The gate is model-free; on_submit runs it synchronously; ~4 min here.
  • Usage table records model, kind, tokens, cache, cost per turn; Codex rows unpriced (0/25).
  • This repo's means: 595k input / 4.7k output / 160 s per reviewer turn; $1.55 per lead chat turn.
  • Plugin ships one skill and one hook; no subagents.
  • Claude Code subagent frontmatter supports model, effort, tools, disallowedTools; CLAUDE_CODE_SUBAGENT_MODEL pins subagent model; usage rolls into modelUsage.
  • Pricing table for current models (API rates), and Anthropic's measured effort/model curves.

Hypotheses that need the measurement phase

  • That Sonnet finds the same blockers as Opus on the scope and verification lenses (the bench decides).
  • That lower reviewer effort does not raise rounds per phase (week 0 tells you).
  • How subscription rate limits weight Sonnet/Haiku vs Opus turns on your plan.
  • The Codex CLI's effort flag name (-c model_reasoning_effort=…) — check codex exec --help.
  • That a Haiku test-runner subagent materially shrinks a long impl turn's context (compare modelUsage before/after).
  • That the digest card is what brings the cockpit back into daily use (hallway test: ten seconds to say what happened).

Questions for you

  1. Is the roadmap order above acceptable in principle: measure (55), bench (56), then policy/kit/cockpit? Or do you want the cockpit pass first because you would use it daily?
  2. Codex is lead and Claude is reviewer right now. Should the bench run the reviewer cells on Claude only (where effort and subagents are verifiable), or on both providers?
  3. For the phase cost block: is API-equivalent dollars the right unit to print, or would you rather see tokens and window percentage only, to avoid a misleading number on a subscription?
  4. Do you want the Aegis event stream (features #13) in scope for tagteam, or should Aegis read tagteam's DB directly?
